## 1. Tasks

### O1 — Preflight learns about `.env`, the clock, and memory

All three additions follow the script's own philosophy (lines 2–15): *check, never install; collect everything; turn a mid-deploy failure into a pre-deploy one.*

1. **`.env` completeness.** Derive the required key set from the one place that actually enforces it — `docker-compose.yml`'s `${VAR:?}` interpolations: `grep -oE '\$\{[A-Z0-9_]+:\?' docker-compose.yml`. For each required key: missing `.env` → "run `scripts/gen-secrets.sh`"; present but missing keys → "re-run `scripts/gen-secrets.sh` (no flags — it appends only what is missing, no PIN rotation)"; a `CHANGEME` placeholder value → name it and point at gen-secrets. Deriving from the compose file means a future key added to compose is caught with **no preflight edit** — the single-source rule the pack applies everywhere else.
2. **Clock sync, warn-only.** Linux: `timedatectl show -p NTPSynchronized` when available; macOS: skip the check and print the runbook's manual line (`sntp -sS time.apple.com`). Warn, don't fail — the runbook's wording ("check before deploying, don't just assume") is a warning posture, and a false positive here must not block a deploy. State *why* in the message: drift presents as certificate errors, not time errors.
3. **Memory, warn-only.** Linux: `MemTotal` < 12 GiB → warn with the measured steady-state figure (~11 GiB) and the runbook reference; macOS: `sysctl -n hw.memsize`, same threshold. Warn-only for the same reason: Docker Desktop VMs make host RAM an approximation.
4. Failures list stays hard-fail for tools and `.env`; the two warn-only checks print under a separate "warnings" banner so exit 0 still means "deployable".

**Verify:** review + run on a host with a doctored `.env` (three cases: absent, key-missing, placeholder). `tests/` gets no new pytest — preflight is bash and out of the pytest surface; its check is being run by `hurl/run-linkup.sh` on every deploy.
**Risk:** low. One caveat: the grep-derived key set includes keys required only by `demo`-profile services — which is *correct* today (compose interpolates `${VAR:?}` file-wide before profile filtering, the exact trap the README documents; if the console plan's C1 later relaxes the console's references to `${VAR:-}`, those keys drop out of the derived set automatically — the derivation stays right on both sides of that change).

### O2 — `scripts/demo.sh`: the Tier-1 wrapper

One script, the runbook's Steps 1–5 in order, ~40 lines, no new logic:

```
preflight → gen-secrets (skip if .env complete) → deploy.sh → seed.sh
→ acceptance.sh → console.sh up → print: console URL, out/application-<nin>.json
  path, the three admin-UI URLs, and "next: docs/exercises.md"
```

- Prints the expected duration before the deploy step (~9–10 min, from the runbook's measured figures) and stage-stamps each step, so silence reads as normal.
- **Refuses on a running federation** (same probe `verify.sh --live` uses, verify.sh:66–72) with the runbook's resume line (`docker compose … up -d`) — the wrapper must not become a way to accidentally re-run the non-idempotent Hurl stand-up against configured state (runbook Teardown: `409 init_already_initialized`).
- Flags: `--skip-console`. Not a replacement for the runbook steps — the header comment says it wraps them for first contact, and names each script it calls, so the wrapper *teaches* the sequence rather than hiding it.
- `runbook.md` Steps section gains one leading line: "First time? `scripts/demo.sh` runs steps 1–5 below and tells you what it is doing."

**Verify:** one `--full`-equivalent manual run on a clean host (this *is* the from-zero path); `--fast` unchanged.
**Risk:** low-medium: the refusal probe must be reliable, or the wrapper reintroduces the 409 trap it exists to avoid — reuse `verify.sh`'s exact probe + bounded retry rather than writing a new one.
