## 2. Proved live, on a running federation

Everything in this section was exercised against the real stack, not only
against tests.

### Item 5 — the generated `local.ini`
Cold `--full` deployed the whole federation from the generated file, and all
four Security Servers were then inspected directly: each carries
`server-conf-cache-period = 5` under a `# GENERATED by hurl/generate.py`
header, so the generated file fully replaced the packaged one.

*Not measured:* that 5s still produces the 4.5–5.6s ACL lag
`docs/decisions/xroad-770-notes.md` §6 recorded for the hand-written ini.
The value reaches the proxy; its *effect* was not re-timed.

### Item 1 — the SSRF guard
Four live submissions through the running join API:

| `spec_url` | Result |
| --- | --- |
| `http://cs:4000/api/v1/clients` | REJECTED `spec_url_origin` — host not allowlisted |
| `http://169.254.169.254/latest/meta-data/` | REJECTED `spec_url_origin` — IP literal |
| `file:///pack/.env` | REJECTED `spec_url_origin` — scheme |
| `http://app-ptsb:8000/spec.yaml` | SUBMITTED, baseline captured |

*Not proved live:*
- the `servers[].url` half. It is unit-tested, but no live spec was served
  with a forbidden backend URL inside it.
- `follow_redirects=False`. Asserted against the source; never exercised
  against an actual 302 from an allowlisted host to `cs:4000`, which is the
  attack it exists to stop.

### Item 3 — the rate limit
Live against the running API: request 31 on one credential returned
`429` with `Retry-After: 2`; the shared applicant token was unaffected;
`GET /catalogue` on the exhausted credential still returned 200; the bucket
refilled a token after ~2s exactly as the rate predicts.

*Not proved live:*
- **the 200-record store quota.** Unit-tested only. Nothing has run against
  a real `out/join/` at the ceiling.
- **concurrency.** `_BUCKETS` is guarded by a `threading.Lock` that no
  parallel request has ever contended for; every live check was serial.

### Item 6 — per-agency tokens
Live: issued a `ptsb` credential (returned once, 32 chars), listed it
(names and dates, no hashes), read `/catalogue` with it, was refused
`/requests` with it, revoked it, and the very next request returned 403.
`submitted_by: ptsb` was recorded on both an accepted and a rejected
submission.

*Not proved live:* nothing renders `submitted_by` in the console's join tab
— only the API response was checked. The console still authenticates with
the shared token, deliberately and untouched.

### Item 4 — `refresh`, and the exercise-3 loop
Ran end to end against a real joined PTSB:

```
drift    -> no drift (1 endpoint(s), unchanged since join)          exit 0
(add /awards/{nin}/history to apps/specs/ptsb-awards.openapi.yaml)
drift    -> DRIFT since join, + /awards/{nin}/history
            remedy with: scripts/member.sh refresh ptsb             exit 1
refresh  -> refreshed service description 15, recorded on the record
drift    -> DRIFT since join AND clean since the last refresh       exit 0
```

X-Road's own published endpoint set moved from `['**', '/awards/*']` to
`['**', '/awards/*', '/awards/*/history']`, which is what proves the refresh
reached the *federation* and not merely the record. `endpoint_baseline`
stayed `['/awards/{nin}']` throughout.

The governance refusal was proved too: with a `POST /awards` added to the
served spec, `refresh` refused by name, and **neither** the federation's
published endpoints **nor** the join record changed — the check runs before
any mutation.

*Not proved live:*
- a member with **more than one** service description. PTSB published one,
  so the per-description loop ran once.
- the "refreshed, but no ACTIVE record to amend" branch (prints to stderr,
  exits 0).
- `refresh` against an **own-server** member.

## 3. Not verified live at all

### Item 2 — the archive export (`b46f00c`)
**This is the largest open gap.** The retirement instruction now prints a
`docker run ... tar czf` of `kp2-<key>-archive` into `out/retired/` before
the `docker volume rm`. Not one of those commands has been run.

The exercise-3 loop could not close it: PTSB joined **hosted** on `ss-plr`,
and `retire_instruction()` correctly returns `None` for a hosted member —
confirmed live in this session's un-join, which reported
`retire_instruction: None`. The export only exists for a member that owns
its own Security Server.

**To close it:** an own-server join (`security_server.own_server: true`,
`scripts/join-agent.sh`), then `DELETE /members/<key>`, then actually run
the printed block and confirm the tarball exists and is **non-empty**. The
plan asked for exactly that and it has not been done.

The conformance status moved to `simulated` on the strength of the code, not
of a run. If the export turns out not to work, `docs/path-conformance.yaml`
`GX.4` is currently overstating the pack.

## 4. Things that are not bugs, so nobody re-debugs them

- **Mid-loop, `pytest` showed 60 failures.** That was the joined PTSB being
  live-but-uncommitted in the working tree — the exact window
  `docs/production-delta.md` names. They cleared the moment the member was
  removed. Not a regression; do not chase it.
- **`onboarding/ptsb/` survives an un-join by design.** `scripts/member.sh`'s
  own comment explains why: it is evidence of what the operator revoked. It
  was deleted by hand at the end of this session only to restore the
  checkout.
- **`scripts/member.sh refresh` has no unit tests for its admin-API half.**
  Deliberate, and stated in the plan: it needs a live Security Server.
  `tests/test_member_drift.py` covers the *reporting* logic offline (six
  cases); the session/refresh/record-amendment path is proved by running
  exercise 3, and by nothing else.
