# Generating prompt — module 2.4 (Register PLR and publish the enrolment service)

**Building block(s):** member-plr
**Produces:** `configs/member-plr/2.4.yaml`
**Public spec:** NIIS X-Road subsystem registration; OpenAPI 3 service descriptions; access rights (ACL)

## Problem

The Learner Registry is the authoritative source of enrolment. It must be
registered on the bus, publish its enrolment API as an X-Road service, and grant
access to exactly one consumer. This is the bb-config-gen member-onboarding play at
its highest-stakes point: the ACL decides whose calls resolve. Precondition: PLR
has passed the Member Requirements checklist (Module 5.2) and its service levels
are set in a signed SLA (Module 5.3; Interop Toolkit).

## Prompt (copy-paste ready)

```
Below is the NIIS X-Road reference for subsystem registration, OpenAPI3 service
descriptions and access rights, the Progressa service brief for the Learner
Registry (PLR), and the enrolment entity from the semantic map [paste all three].

Generate the provider-registration configuration as a single YAML document:
(1) member/subsystem identity is frozen in manifest.yaml's identity.members
    block (code, name, subsystem code, subsystem description) — an input to
    this prompt, not something it generates. Do not restate it;
(2) security_server — code and DNS name; optionally hosted_on, if this
    agency will not run its own Security Server, naming the one that
    hosts it instead;
(3) services — the enrolment API: service code and OpenAPI3 spec URL only. The
    forwarding URL, enabled state and TLS-verify are not config fields: the
    Security Server reads the forwarding target from the spec's own servers.url
    and always enables a published service explicitly, so a value here would be
    a second, driftable copy;
(4) access — the ACL: exactly the consumer subsystems the access policy names
    (for this slice: the examination authority only);
(5) semantic — the entity, key and field list this service returns, copied from
    the semantic map (what 'enrolment' means on this bus).

Rules: every identifier is [confirm: verify against the live X-Road registry] — a
wrong code silently routes nowhere or to the wrong agency. The ACL is a whitelist:
list only who the policy grants, never who might be convenient. Output only the
YAML document.
```

## Inputs / outputs

- **Inputs:** the specs + the PLR service brief + the semantic map (enrolment
  entity) + the access policy.
- **Output:** `configs/member-plr/2.4.yaml`, applied by `scripts/deploy.sh`.

## Safeguard

Verify the ACL both ways after deploy: the authorised consumer (PNEA:EXAMS) can
call, and an unauthorised subsystem (MOEYS:PEMIS) is denied. An ACL that only
proves the happy path is half a check — the deny is what protects citizen data.
