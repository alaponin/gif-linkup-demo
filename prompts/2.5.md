# Generating prompt — module 2.5 (Register PNIA and publish the identity service)

**Building block(s):** member-pnia
**Produces:** `configs/member-pnia/2.5.yaml`
**Public spec:** NIIS X-Road subsystem registration; OpenAPI 3 service descriptions; access rights (ACL)

## Problem

The National Identity Authority owns the person identity every sector reuses. It
must be registered, publish its identity API, and grant access to exactly one
consumer. Identity is the most sensitive service on the bus — the ACL and the
field list carry the legal layer. Precondition: PNIA has passed the Member
Requirements checklist (Module 5.2) and its service levels are set in a signed
SLA (Module 5.3; Interop Toolkit).

## Prompt (copy-paste ready)

```
Below is the NIIS X-Road reference for subsystem registration, OpenAPI3 service
descriptions and access rights, the Progressa service brief for the National
Identity Authority (PNIA), and the person entity from the semantic map [paste all
three].

Generate the provider-registration configuration as a single YAML document:
(1) member/subsystem identity is frozen in manifest.yaml's identity.members
    block (code, name, subsystem code, subsystem description) — an input to
    this prompt, not something it generates. Do not restate it;
(2) security_server — code and DNS name; optionally hosted_on, if this
    agency will not run its own Security Server, naming the one that
    hosts it instead;
(3) services — the identity API: service code and OpenAPI3 spec URL only. The
    forwarding URL, enabled state and TLS-verify are not config fields: the
    Security Server reads the forwarding target from the spec's own servers.url
    and always enables a published service explicitly, so a value here would be
    a second, driftable copy;
(4) access — the ACL: exactly the consumer subsystems the access policy names
    (for this slice: the examination authority only);
(5) semantic — the entity, key and field list, copied from the semantic map. The
    field list is a legal decision: only the fields the credential purpose needs
    (purpose limitation, per the decree) — not the full identity record.

Rules: every identifier is [confirm: verify against the live X-Road registry].
Do not add fields the purpose does not need; do not widen the ACL. Output only the
YAML document.
```

## Inputs / outputs

- **Inputs:** the specs + the PNIA service brief + the semantic map (person
  entity) + the access policy.
- **Output:** `configs/member-pnia/2.5.yaml`, applied by `scripts/deploy.sh`.

## Safeguard

This service returns citizen identity. Two checks before deploy: the field list
matches the decree's purpose limitation exactly, and the ACL denies everyone the
policy does not name. A wrong member code here can route one citizen's data to a
service that asked about another — the single highest-stakes [confirm] in the pack.
